# 2. Core Mission Directive

Build an AI-powered "Smart Campus Lost & Found" system. The application must completely automate the tedious process of reconnecting students with their lost items by ingesting multimodal data (images and text) and utilizing LLM reasoning to identify likely matches between "Lost" and "Found" item databases.

---

# 3. Product Goal

To provide a centralized, highly intelligent campus platform where users can submit reports of items they have lost or found. The system leverages Gemini's multimodal capabilities to analyze photos, descriptions, locations, and times, automatically calculating a "Match Confidence Score" and generating a human-readable explanation for why two items are considered a potential match.

---

# 4. Mandatory Features

* **Multimodal Reporting:** Users can submit lost or found items including a photo, text description, location, and time of the event.
* **Automated AI Matching Engine:** A backend service that automatically compares new "Lost" items against existing "Found" items (and vice versa) using Gemini.
* **Confidence Scoring & Explanation:** The AI must output a precise confidence score (0-100%) and a short, logical explanation detailing *why* the items match based on visual and textual features.
* **Search & Discovery:** A dedicated interface allowing users to manually search, filter, and discover relevant lost and found reports.
* **Match Dashboard:** A dedicated view for a specific item showing its top AI-generated matches sorted by confidence score.

# 6. Application Pages (Routes)

1. **`/` (Home/Dashboard):** Overview of recent lost and found items, quick stats, and primary Call-To-Action buttons.
2. **`/report/lost`:** Form to submit a newly lost item (requires image, text, location, time).
3. **`/report/found`:** Form to submit a newly found item (requires image, text, location, time).
4. **`/search`:** Feed of all items with filters (Type, Category, Date Range) and a text search bar.
5. **`/item/:id`:** Detailed view of a specific item, displaying its data, uploaded image, and an auto-generated section showing "Top Potential Matches" with AI confidence scores and explanations.

---

# 7. User Flow

1. **Submission:** A user loses a blue water bottle. They navigate to `/report/lost`, upload a photo of a similar bottle, describe it, and submit the time and location they lost it.
2. **Processing:** The backend saves the item to PostgreSQL, then triggers the AI Matching Engine in the background.
3. **Matching:** The AI queries the database for recent "Found" items in the same general category, compares the multimodal features of the new item against the found items, and saves the match results.
4. **Resolution:** The user is redirected to `/item/:id`, where they see a "95% Match" with a found item, along with the AI's explanation: *"Both items are 32oz blue Hydroflasks with a distinct dent on the base; locations (Library and Quad) are adjacent."*

# 10. Database Schema (Production SQL for PostgreSQL)

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

CREATE TABLE items (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    report_type VARCHAR(10) NOT NULL CHECK (report_type IN ('lost', 'found')),
    category VARCHAR(50) NOT NULL,
    title VARCHAR(255) NOT NULL,
    description TEXT NOT NULL,
    image_url TEXT NOT NULL,
    location VARCHAR(255) NOT NULL,
    event_time TIMESTAMP WITH TIME ZONE NOT NULL,
    contact_info VARCHAR(255) NOT NULL,
    status VARCHAR(20) DEFAULT 'active' CHECK (status IN ('active', 'resolved')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE item_matches (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    lost_item_id UUID NOT NULL REFERENCES items(id) ON DELETE CASCADE,
    found_item_id UUID NOT NULL REFERENCES items(id) ON DELETE CASCADE,
    confidence_score INTEGER NOT NULL CHECK (confidence_score >= 0 AND confidence_score <= 100),
    explanation TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(lost_item_id, found_item_id)
);

CREATE INDEX idx_items_report_type ON items(report_type);
CREATE INDEX idx_items_category ON items(category);
CREATE INDEX idx_matches_lost_id ON item_matches(lost_item_id);
CREATE INDEX idx_matches_found_id ON item_matches(found_item_id);

```

# 11. Row Level Security (RLS) / Data Isolation Rules

* Ensure all database queries use parameterized inputs to prevent SQL injection.
* If implementing standard PostgreSQL without an auth layer, ensure that updates or deletions of items require a verification token or are restricted. (For this MVP, assume public read/write, but strict payload validation via Zod).
* The `item_matches` table must only be written to by the backend AI service, never directly from a client request.

---

# 12. Backend API Routes

* `GET /api/items`: Fetch items with optional query params `?type=lost&category=Electronics`.
* `GET /api/items/:id`: Fetch a single item by UUID.
* `POST /api/items`: Create a new item. **Crucial:** After saving to the DB, this route must asynchronously trigger the `AI Matching Engine` before returning the `201 Created` response.
* `GET /api/items/:id/matches`: Fetch AI-generated matches for a specific item, sorted by `confidence_score` DESC.
* `POST /api/trigger-match/:id`: Manual trigger to run the AI matching algorithm for a specific item ID against the database.
